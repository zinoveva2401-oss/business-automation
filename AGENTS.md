# Инструкции для AI-агентов

`AGENTS.md` — единый модельно-нейтральный контракт проекта. Модельные адаптеры дополняют, но не переопределяют его.

## Приоритет источников

При противоречии используйте порядок:

1. Последнее явное решение владельца.
2. Утверждённая задача или активный handoff.
3. Доменный `SOURCE_OF_TRUTH`.
4. [`docs/ai/PROJECT_MAP.md`](docs/ai/PROJECT_MAP.md).
5. Этот файл.
6. Модельно-специфичный адаптер.
7. Остальные материалы.

Результаты сборки, QA и временные артефакты не являются источниками истины.

## Рабочий цикл

**UNDERSTAND TASK → READ MINIMUM → CHECK CAPABILITY → SELECT EXISTING TOOLS → ACT MINIMALLY → VERIFY → HANDOFF / STOP**

1. Если существует `docs/ai/handoffs/ACTIVE_HANDOFF.md`, прочитайте его до повторного исследования.
2. Начните навигацию с `docs/ai/PROJECT_MAP.md`; не сканируйте весь репозиторий без необходимости.
3. Сверьте доступные средства с [`docs/ai/AI_CAPABILITIES.md`](docs/ai/AI_CAPABILITIES.md).
4. Используйте подходящий существующий компонент, навык или инструмент.
5. Вносите минимальные изменения только в рамках задачи и проверяйте результат.
6. При передаче или остановке следуйте [`docs/ai/HANDOFF_PROTOCOL.md`](docs/ai/HANDOFF_PROTOCOL.md).

Не повторяйте исследование, уже выполненное и зафиксированное вышестоящей ролью. Не пересказывайте большие документы, не создавайте варианты вместо утверждённого решения и не переписывайте весь файл ради локальной правки.

## Источники по доменам

Для изменений продукта, бренда, контента, маркетинга или автоматизации найдите нужный источник через `PROJECT_MAP.md`. Основная база знаний находится в `docs/project-knowledge/`, документация сайта — в `docs/site/`, AI-архитектура — в `docs/ai/`.

## Границы ролей

В производстве участвуют владелец, аналитик, контент-завод, фабрика продуктов, арт-директор и другие утверждённые роли. Получив утверждённую задачу или handoff, технический агент не проводит заново редакционную, SEO- или маркетинговую стратегию, продуктовую методологию, решение FREE→PAID, художественную концепцию или бизнес-решение.

При реальном техническом противоречии сообщите `BLOCKER`, не переосмысливая вышестоящее решение.

## Границы изменений и Git

- Работайте только в рамках явно поставленной задачи и сохраняйте утверждённые решения.
- Перед изменениями проверяйте текущий `git diff`; не перезаписывайте чужую работу и не меняйте несвязанные файлы.
- Не создавайте лишние ветки, не меняйте активную ветку без предупреждения и не удаляйте чужие ветки.
- При передаче фиксируйте ветку, статус и последний удачный коммит.
- Коммитьте только после проверки и разрешения, если задача требует утверждения.

## Недостающие возможности

Если подходящего средства действительно нет, сообщите:

```text
CAPABILITY GAP
Что требуется → почему существующего недостаточно → тип средства → существующая альтернатива → обязательное/желательное → ожидаемая польза
```

Не придумывайте название неизвестного инструмента и не устанавливайте Skill, плагин, MCP, расширение, библиотеку или сервис без разрешения владельца.

Если одна проблема регулярно расходует токены, требует одинаковой ручной работы, создаёт повторяющиеся ошибки или вынуждает повторять инструкцию, допустимо предложить:

```text
SYSTEM IMPROVEMENT SUGGESTION
Проблема → решение → где реализовать
```

Самостоятельно архитектуру не меняйте.

## Отчёт

После работы перечислите изменённые файлы, проверки и результаты, известные риски, непроверенное и статус. После выполнения задачи остановитесь или оформите handoff.
