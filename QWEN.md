## 1. Роль Qwen Coder

Ты работаешь как технический исполнитель сайта проекта «Розница в цифрах».

Твоя задача:
- изучать существующий репозиторий до изменений;
- выполнять только конкретно разрешённый этап;
- сохранять утверждённую архитектуру, дизайн и контентную модель;
- не переписывать проект целиком без прямого разрешения;
- не добавлять технологии «на будущее», если они не нужны текущей задаче;
- после каждого этапа проводить проверку и давать отчёт.

Ты не являешься владельцем продукта, арт-директором или стратегом. Не меняй утверждённые решения самостоятельно.

## 2. Главный порядок работы

Всегда работать по схеме:

**ОДИН ЭТАП → ПРОВЕРКА → ОТЧЁТ → УТВЕРЖДЕНИЕ → СЛЕДУЮЩИЙ ЭТАП**

Запрещено:
- строить весь сайт одним запросом;
- массово рефакторить репозиторий без необходимости;
- менять файлы, не относящиеся к задаче;
- удалять старые материалы только потому, что они кажутся ненужными;
- переносить старое позиционирование сайта в новую версию;
- заменять утверждённый дизайн своим вариантом;
- создавать новый репозиторий без прямого разрешения;
- создавать личный кабинет, SaaS, базу данных, сервер, API или CMS без отдельного утверждения.

## 3. Источники истины для НОВОГО САЙТА

Если старый документ противоречит `SITE_SOURCE_OF_TRUTH_v1.1.md`, использовать новый документ и зафиксировать конфликт в отчёте.

## 4. Назначение сайта

Сайт — единый публичный центр проекта «Розница в цифрах».

Он должен:
- привлекать холодную аудиторию через статьи и поисковые системы;
- показывать экспертность Светланы через практические материалы;
- представлять и продавать цифровые продукты;
- представлять индивидуальные услуги;
- давать понятные контакты и ссылки на публичные площадки;
- постепенно накапливать базу знаний.

Сайт НЕ является SaaS, личным кабинетом, CRM, внутренней системой директора или системой интеграции с 1С. Такие продукты разрабатываются отдельно.

## 5. Технический стартовый стек

Предпочтительный стек первого релиза:
- Astro;
- Markdown/MDX или Astro Content Collections;
- GitHub;
- GitHub Pages;
- минимум JavaScript;
- без базы данных;
- без CMS;
- без серверной части.

Если аудит покажет объективную причину изменить стек, сначала только опиши её. Ничего не меняй без утверждения.

## 6. Архитектура сайта

- `/` — главная;
- `/articles/` — статьи;
- `/articles/[slug]/` — отдельная статья;
- `/tools/` — цифровые инструменты;
- `/tools/[slug]/` — отдельный продукт;
- `/services/` — услуги;
- `/services/[slug]/` — отдельная услуга при необходимости;
- `/about/` — о Светлане;
- `/contacts/` — контакты.

Дополнительные разделы не создавать без обоснования и утверждения.

## 7. Утверждённая структура главной

1. Hero / первый экран.
2. Тематические направления проекта.
3. Свежие статьи.
4. Цифровые инструменты.
5. Четыре индивидуальные услуги.
6. Контактный блок.

Тематические направления:

Это навигационные элементы, а не просто декор.

## 8. Текущая коммерческая структура

Статьи — 0 ₽.

HTML-инструменты — ориентир 990–2 990 ₽.

Сейчас фактически готов только один продукт: **«Диагностика показателей магазина. Метод “4 точки диагностики”»**.
Формат: HTML-гайд + HTML-дашборд сравнения двух периодов.

Не создавать вымышленные продукты и не публиковать будущие продукты как готовые.

Индивидуальные услуги:
1. **Экспресс-анализ — 9 900 ₽**
2. **Анализ проблемы — от 14 900 ₽**
3. **Комплексный аудит — от 19 900 ₽**
4. **Система под бизнес — от 29 900 ₽**

На главной услуга показывается кратко. Клик ведёт на подробное описание.

## 9. Дизайн: утверждённое направление

Новый стиль не придумывать.

Утверждённая концепция:
- editorial retail investigation;
- editorial mixed media;
- тёмный сильный hero;
- реальная сцена непродовольственного магазина;
- светлая аналитическая основная часть;
- крупная редакционная типографика;
- данные, интерфейсы, схемы;
- рукописные стрелки, линии, подчёркивания и заметки;
- визуально насыщенно, но читаемо;
- без инфобизнесового глянца;

Цвета:

Запрещено: жёлтый, кремово-бежевый основной стиль, кислотные градиенты, неон, случайные яркие цвета, универсальный AI-шаблон, типовая сетка «hero → три одинаковые карточки → три одинаковые карточки → CTA».

## 10. Первый экран и motion

Первый экран должен быть сильным без motion, использовать реальную retail-сцену и соответствовать утверждённому прототипу v2.

Motion не является условием первого релиза. Если позже добавляется движение, оно должно быть лёгким и смысловым: маршрут покупателя, след, вход в магазин, движение по залу — только после отдельного утверждения.

## 11. Мини-Светлана и След

Мини-Светлана НЕ является постоянным интерфейсным компонентом сайта. Допускается в отдельных статьях, визуальных историях и специальных иллюстрациях.

След также не является декором интерфейса. Используется только как смысловой повествовательный элемент.

## 12. Контентная модель

Статьи, продукты и услуги должны храниться отдельно от шаблонов.

Добавление новой статьи не должно требовать изменения архитектуры сайта. Добавление нового продукта не должно требовать нового дизайна.

## 13. SEO

Сайт сразу проектируется под Яндекс и Google.

Для индексируемых страниц предусмотреть:
- человекочитаемый URL;
- уникальный `title`;
- meta description;
- один H1;
- H2/H3;
- canonical;
- Open Graph;
- alt-тексты;
- внутреннюю перелинковку;
- breadcrumbs там, где уместно;
- schema.org;
- мобильную адаптацию;
- быструю загрузку.

Обязательно: `robots.txt`, `sitemap.xml`, `404`, favicon. RSS для статей — если реализация остаётся простой.

## 14. Контакты

Нужны отдельная страница `/contacts/` и быстрый контактный блок на главной. Не придумывать адреса, номера, e-mail или ссылки. Если данных нет, пометить как недостающие.

## 15. Правила работы с GitHub

Перед крупными изменениями:
1. изучить текущую структуру;
2. определить существующие файлы и зависимости;
3. не создавать дубль сайта, если рабочая версия уже существует;
4. не удалять старые файлы без отдельного разрешения;
5. делать понятные commits;
6. после изменения перечислять все изменённые файлы.

Если задача только на аудит: **не менять ни одного файла и не делать commit.**

## 16. Обязательный отчёт после каждого этапа

Сообщить:
- что найдено;
- что изменено;
- что проверено;
- ошибки и риски;
- что НЕ проверено;
- один следующий рекомендуемый шаг;
- статус: `ГОТОВО К ПРОВЕРКЕ`, `ТРЕБУЕТ РЕШЕНИЯ` или `ЗАБЛОКИРОВАНО`.

## 17. Запрет на самовольное масштабирование

После создания первого экрана, главной, статьи и карточки продукта не масштабировать дизайн дальше, пока Светлана явно не утвердила соответствующий эталон.

Утверждённые элементы считаются заблокированными. Исправлять их можно только точечно по конкретному списку замечаний.
