# PRODUCT_EXECUTION — цифровые продукты «Докрути»

Статус: Действующий production-регламент
Версия: 2.0
Проект: `Докрути`

Этот регламент применяется к HTML-инструментам, калькуляторам, анализаторам, генераторам, панелям, тренажёрам и другим coded/digital продуктам. Текущая методология, продуктовые решения, цены и SKU берутся из live Drive через `docs/ai/SOURCE_MANIFEST.md`, а не из старых repo-копий.

## 1. Класс задачи

### PRODUCT PATCH

Локальная исправимая точка: формула, кнопка, текст, ссылка, responsive или конкретный баг. Читать target и релевантный source; не проводить полный product audit. Проверить воспроизведение дефекта, исправленный сценарий и зависимый build/browser path.

### PRODUCT INTEGRATION

Готовый продукт встраивается в каталог/сайт/выдачу. Проверить паспорт/metadata продукта, target page/renderer, реальный URL, CTA, скачивание/выдачу если она подключена, responsive и build/check. Не менять внутреннюю методологию без отдельного решения.

### PRODUCT DEVELOPMENT

Новый продукт или существенная переработка. До кода определить:

- пользователя и реальную проблему;
- входные данные, обработку и объяснимый результат;
- решение, которое пользователь должен принять после результата;
- следующий шаг и бизнес-ценность;
- минимальный удобный формат и лишнюю сложность;
- необходимость storage, auth, export, AI, charts, integrations и analytics.

Сначала сформировать несколько materially different вариантов, выбрать сильнейший по полезности/понятности/риску/стоимости, затем реализовать. Если исходная идея слабее другого формата, сообщить `ПРОБЛЕМА → ПОЧЕМУ СЛАБО → ЧТО ДЕЛАЕМ → ПОЧЕМУ ЛУЧШЕ` и продолжить с лучшим решением, если owner decision не требуется.

## 2. Пользовательский маршрут

Каждый существенный продукт проектировать как:

`ВХОД → ОБЪЯСНЕНИЕ → ДАННЫЕ/ДЕЙСТВИЕ → ОБРАБОТКА → РЕЗУЛЬТАТ → ПОНИМАНИЕ → РЕКОМЕНДАЦИЯ → СЛЕДУЮЩЕЕ ДЕЙСТВИЕ`.

Пользователь должен понимать значение результата, степень проблемы, причины, первый приоритет и следующий шаг. Дизайн, состояния, ошибки, пустые состояния, onboarding, mobile, accessibility и meaningful interaction являются частью продукта, а не пост-обёрткой.

## 3. Production loop

Для DEVELOPMENT: `BUSINESS/USER PROBLEM → CURRENT SOURCE CHECK → PRODUCT/DONOR RESEARCH → USER JOURNEY → PRODUCT ANALYSIS → FUNCTIONAL/TECHNICAL ARCHITECTURE → UX/DESIGN → PROTOTYPE → INTERNAL REVIEW → BUILD → FUNCTIONAL/UX/VISUAL/DATA QA → SECURITY/PRIVACY → A11Y → PERFORMANCE → RED TEAM → CONSOLIDATED FIX → REGRESSION → RELEASE CANDIDATE`.

Не вставлять AI без доказанной пользы. Сравнить AI с обычным алгоритмом по стабильности, объяснимости, цене ошибки, данным и ограничениям. Не превращать каждый продукт в SaaS, backend, большую БД, auth, subscription или microservices без доказанной необходимости.

## 4. Реальная эксплуатация

Проверить happy path и неправильные/неполные данные, пропуски, крайние значения, повторный вход, потерю соединения, ошибки, пустые состояния, длинный текст, большие данные, back/navigation, сохранение, экспорт, приватность, безопасность и скорость. Для значимого продукта определить только применимые события: start, onboarding complete, finish, abandon, result, recommendation open, export, next product/service и return.

## 5. Release gate

Release candidate не готов при Critical/Major дефекте. Доказать по применимости: методология сохранена, результат полезен и объясним, UX логичен, интерфейс профессионален, mobile/A11Y работают, логика/данные корректны, storage/export безопасны, performance приемлема, analytics не ломается, brand system соблюдена, Red Team и regression выполнены.

Commit/push/deploy или выдача клиенту — только в явном scope задачи после фактических проверок. Финальный отчёт содержит результат, changed files, URL/branch/commit, применимые QA и непроверенные риски.
