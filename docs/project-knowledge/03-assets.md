# 03_Активы_проекта

Версия: 6.2  
Дата: 11.09.2026  
Статус: Действующий реестр устойчивых активов  
Владелец: Светлана Тарасова  
Бренд: `Докрути`  
Источник истины: да — для перечня устойчивых активов и их назначения. Текущие статусы, доступность, тарифы, этапы запуска и техническая готовность всегда сверяются с `Бизнес-системой` и фактической средой.

# 1. Назначение

Документ фиксирует, какие активы принадлежат проекту и какую функцию они выполняют.

Он не хранит как вечные факты временные статусы вроде `настроено / сломано / основной исполнитель / текущая ветка / готово к продаже`.

`Есть аккаунт`, `есть файл`, `подключено`, `работает` и `проверено end-to-end` — разные состояния.

# 2. Мастер-бренд и домены

Мастер-бренд: `Докрути`.

Латиница: `DOKRUTI`.

Домены бренда:

- `dokruti.ru` — основной латинский домен;  
- `докрути.рф` — кириллический домен бренда.

Домен считается технически работающим только после фактической регистрации, DNS/SSL-настройки, подключения к production и QA. Само наличие имени в реестре активов не равно технической готовности.

# 3. Бизнес-система

Google Sheet `Бизнес-система` — главный оперативный Control Center проекта.

В нём хранятся текущее состояние, цель, блокеры, рабочий реестр, решения, деньги, зависимости, конкуренты/референсы и `NEXT ACTION`.

После значимого подтверждённого изменения состояния при доступе на запись этот источник обновляется автоматически, без отдельного напоминания Светланы.

# 4. Google Drive и база знаний

Google Drive — долгоживущее хранилище актуальных документов, исследований, masters, материалов и рабочей базы.

Ключевые нормативные документы текущей архитектуры:

- `00_Индекс_базы_знаний`;  
- `00_Ядро_проекта`;  
- `01_Обо_мне`;  
- `02_Бренд-система`;  
- `03_Активы_проекта`;  
- `04_Продуктовая_карта`;  
- `06_Архитектура_ИИ_и_автоматизации`;  
- `08_Дизайн-система_продуктов`.

Главный брендовый и визуальный source of truth — `02_Бренд-система`.

Отдельные старые документы про социальный визуал, визуальный паспорт и лид-магнит после переноса действующих правил удалены из рабочей папки 11.09.2026 и больше не являются активами нормативной базы.

# 5. Сайт

Сайт — собственный центральный цифровой актив `Докрути`: бренд, знания, статьи, продукты, органический поиск, доверие и коммерческие маршруты.

Сайт должен работать на домене `dokruti.ru`; `докрути.рф` используется как второй брендовый домен/редирект или в другой корректной технической роли после настройки.

Текущие staging/production URL, ветка, HEAD, хостинг, SSL, SEO, canonical, sitemap и фактическая готовность не фиксируются здесь навсегда. Они проверяются по текущей технической среде и `Бизнес-системе`.

Сайт должен развиваться по новой стратегии `Докрути`, а не только получить новое название и цвета.

# 6. Контент-система

Действующая Контент-система — операционный актив для тем, исследований, производства, адаптаций, публикаций, связей с продуктами и метрик.

Её конкретное имя, структура и техническая реализация могут меняться. Используется фактически актуальная версия, а не старое название из архивного документа.

Контентный актив должен поддерживать многоканальную модель `Докрути`, а не одну вечную схему `ARTICLE-FIRST / SITE-FIRST / SOCIAL-FIRST`.

# 7. Код, репозитории и технические исходники

GitHub, локальные репозитории и иные кодовые источники используются там, где сайт, продукт или автоматизация действительно требуют кода.

Перед технической работой обязательно проверить:

- фактический source of truth;  
- репозиторий/путь;  
- ветку и актуальный HEAD;  
- наличие незакоммиченных изменений;  
- доступ на чтение/запись;  
- исполнителя и его лимиты;  
- возможность QA и отката.

Наличие копии в GitHub не доказывает, что она новее локального или deployment-source состояния.

# 8. ChatGPT, Skills и агенты

ChatGPT Project `Бизнес-система` — рабочая среда владельца.

Профильные Skills и агентные контуры могут включать Business OS, Фабрику продуктов, Аналитика, Контент-завод, Арт-директора и другие подтверждённые специализации.

Skill не считается доступным для изменения только потому, что он известен проекту. Перед внешним изменением обязателен `ENVIRONMENT CHECK`.

Будущая архитектура должна снижать ручное переключение между чатами, моделями и инструментами: владелец формулирует бизнес-задачу, а система сама выбирает минимально достаточный маршрут.

# 9. Производственные инструменты

Обычный чат, Work, Codex, браузерные/desktop-коннекторы, Canva, Adobe, Descript, Remotion/HyperFrames, HeyGen, генераторы изображений, Qwen, OpenCode/Ollama и другие инструменты могут использоваться по задаче.

Ни один из них не является вечным обязательным исполнителем.

Выбор делается по фактической доступности, качеству, скорости, полной стоимости, безопасности, совместимости, лимитам и возможности проверки результата.

# 10. Публичные площадки бренда

К существующему публичному контуру `Докрути` относятся:

- сайт;  
- VK;  
- Telegram;  
- Дзен;  
- Instagram;  
- VC.ru;  
- MAX;  
- YouTube и другие площадки, если они фактически используются и дают пользу.

Конкретная площадка не становится обязательным узлом каждой воронки.

Роль, приоритет, частота, формат и следующий шаг определяются `02_Бренд-система`, текущей контентной стратегией и фактическими данными.

Каждая площадка получает нативную упаковку, а не механическую копию одного шаблона.

# 11. Визуальные активы

Верхний визуальный source of truth: `02_Бренд-система`.

К устойчивой визуальной базе относятся:

- master visual principle `ДОКРУТИ + оранжевый След + точка результата`;  
- актуальная палитра бренда;  
- фирменный След;  
- реальные фотографии Светланы;  
- утверждённые референсы лица/образа Светланы;  
- Master Character Pack Мини-Светланы, пока он остаётся действующим;  
- `VISUAL_RUNTIME_PACK` и действующий Art Director Skill как производственная база, если они не конфликтуют с более новым мастер-брендом;  
- Visual Event First, Remove-Text Test, motion и anti-degradation QA как производственные принципы.

Старый `retail-first` и старый `MASTER-REFERENCE 01 — Editorial Retail Investigation` не являются глобальным визуальным default мастер-бренда. Retail Investigation может использоваться как предметный режим для материалов про розницу.

При конфликте приоритет: последнее решение Светланы → `02_Бренд-система` → актуальная задача → профильный Skill/Runtime.

# 12. Продуктовые активы

Каждый активный продукт должен иметь один канонический source of truth для содержания, версии и ключевых производственных артефактов.

Старый HTML, PDF, таблица, цена или обложка не получают приоритет только потому, что уже существуют.

Текущий активный продукт и его стадия берутся из `Бизнес-системы` и source of truth конкретного продукта.

Продуктовые классы и долгосрочное направление портфеля хранятся в `04_Продуктовая_карта`, а не в этом реестре.

# 13. Оплата, CRM, выдача и клиентский контур

Конкретная CRM, платёжный провайдер, чековый контур, выдача и автоматизация не закрепляются здесь навсегда.

Любой сервис считается рабочим только после фактической проверки нужной цепочки.

Регистрация аккаунта не равна работающей CRM; созданная форма не равна рабочей оплате; описанный webhook не равен автоматической выдаче.

# 14. Аналитика

Счётчики, кабинеты и источники данных являются активами только в рамках фактически работающей аналитической цепочки.

Подключённая Яндекс.Метрика или другой отдельный источник сам по себе не означает сквозную аналитику.

Цель — связать контент/источник → действие → продукт → покупку → выручку → повторные покупки и выводить управленческие агрегаты в `Бизнес-систему` без хранения лишних персональных данных.

# 15. Интеллектуальные и репутационные активы

В стратегический актив бренда входят не только файлы и сервисы, но и накапливаемый интеллектуальный капитал:

- авторские комбинации и адаптации, профессионально проверенные и корректно оформленные;  
- методические материалы и библиотеки решений;  
- книги и публикации;  
- кейсы с подтверждёнными данными;  
- публичные выступления и интервью;  
- профессиональные дипломы/сертификаты, реально усиливающие компетентность;  
- партнёрства и профессиональная репутация;  
- база клиентов и аудитория в законно допустимом контуре.

# 16. Владение, доступ, восстановление и права

Критические активы бренда и бизнеса должны оставаться под владельческим или администраторским контролем Светланы/`Докрути`. Внешний подрядчик, сотрудник, агент или технический исполнитель не должен быть единственным владельцем домена, хостинга, репозитория, рекламного кабинета, базы клиентов, платёжного/аналитического контура или другого актива, потеря которого остановит бизнес.

Для критических активов по применимости должны существовать: понятный владелец; способ восстановления доступа; актуальные резервные контакты/механизмы восстановления; возможность экспорта или резервного копирования данных и исходников; понятный путь передачи/смены исполнителя или сервиса; проверяемый способ восстановления после сбоя. Резервная копия считается полезной только если её можно фактически восстановить.

Доступ выдаётся по принципу минимально необходимого: агент, подрядчик или сервис получает только те права и данные, которые нужны конкретной задаче. Пароли, токены, ключи API, коды восстановления и иные секреты не хранятся в открытых проектных документах, промптах или общедоступных рабочих файлах; для них используется защищённый контур хранения.

Для внешних и созданных с помощью ИИ материалов, когда это юридически или коммерчески значимо, сохраняются происхождение, источник и право использования: лицензия, разрешение, условия сервиса, собственный исходник или иное достаточное основание. Наличие файла само по себе не доказывает право на коммерческое использование.

# 17. Что не хранить здесь как постоянный факт

Не заносить навсегда:

- текущий NOW/NEXT;  
- текущую цену;  
- временный список продуктов;  
- текущий статус покупки домена/настройки DNS;  
- текущую ветку/кодера;  
- временный тариф;  
- одноразовый технический дефект;  
- краткосрочный контент-план;  
- текущий канал-приоритет;  
- текущий статус `готово к продаже`.

Для этого используется `Бизнес-система` и фактические source of truth.

# 18. Что нельзя считать готовым без проверки

Без фактического QA не считать работающими:

- домен — только по факту регистрации и технического открытия;  
- сайт — только по факту live QA;  
- оплату — только по успешному платёжному тесту;  
- чек — только по фактической законной выдаче;  
- продукт — только по конечному файлу/системе и пользовательскому QA;  
- автоматическую выдачу — только по end-to-end тесту;  
- CRM — только по фактической записи/обработке нужного события;  
- аналитику — только по прохождению данных по цепочке;  
- автоматизацию — только по выполненному workflow;  
- код — только по проверенному результату в целевой среде;  
- Skill — только по runtime-проверке, если от него зависит работа.
