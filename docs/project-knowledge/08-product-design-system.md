# 08_Дизайн-система_продуктов

Версия: 5.1  
Дата: 11.09.2026  
Статус: Действующая продуктовая UX/visual-система  
Владелец: Светлана Тарасова  
Бренд: `Докрути`  
Источник истины: да — для пользовательского, визуального и производственного качества продуктов после выбора продуктовой стратегии и формата.

# 1. Назначение

Документ отвечает на вопрос: `как выбранный продукт Докрути превратить в понятный, профессиональный и удобный пользовательский опыт`.

Он не выбирает:

- какой продукт запускать;  
- его цену;  
- текущую очередь;  
- коммерческую стратегию;  
- обязательный формат;  
- конкретный производственный сервис.

Эти решения принадлежат Фабрике продуктов, `Бизнес-системе` и source of truth конкретного продукта.

Верхний брендовый/визуальный источник — актуальная `02_Бренд-система`.

# 2. Иерархия решений

При конфликте:

1. последнее прямое решение Светланы по текущему продукту;  
2. актуальный source of truth продукта и утверждённые product/format decisions;  
3. `02_Бренд-система`;  
4. действующий Skill Фабрики продуктов;  
5. действующий Skill Арт-директора / актуальный Visual Runtime;  
6. этот документ;  
7. старые макеты и архивные референсы.

Старый продукт не становится эталоном только потому, что раньше был утверждён.

# 3. Формат выбирается до дизайна

Допустимы электронная книга, рабочая книга/таблица, web/HTML, приложение, калькулятор, тренажёр, курс, комплект, библиотека, сервис и другие форматы.

Ни PDF, ни Excel/Google Sheets, ни HTML/web, ни Canva не являются default.

Формат оценивается по:

- задаче и результату пользователя;  
- удобству применения;  
- сложности логики;  
- необходимости ввода/расчётов;  
- целевому устройству;  
- обновляемости;  
- стоимости и скорости производства;  
- поддержке;  
- продаже и выдаче.

Если продукт комбинированный, каждый компонент должен иметь отдельную функцию. Нельзя добавлять файлы только ради ощущения «больше ценности».

# 4. Прототип до массовой сборки

Для сложного продукта до полной сборки выбираются репрезентативные реальные страницы/экраны, достаточные для проверки UX и визуального принципа.

Количество определяется задачей, а не магическим числом.

Прототип использует настоящее содержимое, а не lorem ipsum и декоративные пустые блоки.

Проверяются по необходимости:

- сложная смысловая страница;  
- расчёт/таблица/логика решения;  
- пользовательский ввод;  
- состояние ошибки/пустых данных;  
- результат и следующий шаг;  
- мобильный/узкий экран, если продукт digital.

Светлана утверждает принцип пользовательского опыта и значимые брендовые решения, а не каждый декоративный пиксель.

После freeze производственный исполнитель не переизобретает продуктовую методологию.

# 5. Наследование бренда `Докрути`

Каждый продукт принадлежит `Докрути`, но не обязан выглядеть как копия сайта или другого продукта.

Наследуются:

- wordmark/брендовая подпись, когда она нужна;  
- фирменный След и точка результата как смысловые элементы;  
- актуальная палитра и типографическая логика;  
- взрослый editorial-характер;  
- причинность и движение к решению;  
- `VISUAL EVENT FIRST → INFORMATION INSIDE EVENT`;  
- `REMOVE-TEXT TEST` для визуальных сцен;  
- отсутствие шаблонного инфобизнесового глянца;  
- требования к реальности данных и кейсов;  
- общий уровень качества `Докрути`.

Не обязаны повторяться одинаково:

- композиция;  
- фон;  
- число карточек;  
- тип обложки;  
- присутствие Светланы;  
- Mini-Светлана;  
- конкретная предметная среда;  
- motion;  
- структура страниц.

У продукта должен быть свой визуальный сюжет, если это помогает содержанию.

# 6. Предметная среда

Старый `retail-first` отменён как универсальный default.

Среда выбирается по содержанию продукта:

- розница → реальная торговая среда;  
- закупки/опт → поставки, ассортимент, склад, переговоры, документы;  
- производство → реальный производственный/операционный контекст;  
- кросс-отраслевая тема → соответствующий процесс, рабочие документы, данные, люди или нейтральная реальная бизнес-среда;  
- цифровая тема → настоящий интерфейс/данные/процесс.

Не использовать случайный офисный сток, стерильные AI-сцены, пачки денег, ложные интерфейсы и предметы, не соответствующие теме.

# 7. Пользовательский маршрут

У продукта должен быть понятный путь:

`вход → что это → что делать → какие данные/действия нужны → результат → что он означает → что делать дальше`.

Если пользователь не понимает следующий шаг без объяснения Светланы, продукт не готов.

Для комбинированного продукта связь компонентов должна быть явной: когда открыть следующий инструмент, что перенести, откуда взять данные и как вернуться к основному маршруту.

# 8. Электронная книга / методический материал

Книга или методический продукт не должен быть стеной текста.

Крупный содержательный блок по необходимости включает:

- реальную ситуацию/проблему;  
- объяснение причины;  
- метод/логику решения;  
- ограничения;  
- пример;  
- действие пользователя;  
- инструмент/ссылку, если нужен;  
- следующий шаг.

Визуальный ритм подчинён содержанию, а не шаблону.

Недопустимы:

- сплошные стены текста без иерархии;  
- декоративные изображения без функции;  
- микрошрифт;  
- ложные кейсы;  
- графики без данных;  
- механическое повторение одного шаблона на десятках страниц;  
- заметная деградация качества к концу.

# 9. Таблица / калькулятор / рабочий инструмент

Первый пользователь без автора должен понимать для каждого значимого поля:

- что вводить;  
- откуда взять данные;  
- формат/единицу;  
- пример;  
- что делать при отсутствии данных;  
- что рассчитывается/показывается;  
- как трактовать результат;  
- какое действие следует дальше.

Формулы и выводы тестируются на обычных, крайних и ошибочных сценариях.

Недостаток данных должен приводить к честному состоянию `недостаточно данных`, а не к псевдоточному выводу.

# 10. Web / HTML / приложение

Для интерактивного продукта обязательны по применимости:

- понятный первый экран;  
- минимально достаточный ввод;  
- видимый статус действия;  
- обработка пустых и ошибочных данных;  
- объяснимый результат;  
- отсутствие тупиков;  
- адаптация под целевые устройства;  
- сохранение утверждённого смысла при технической сборке;  
- проверка кнопок, формул, переходов и состояний;  
- безопасность и работа с данными по задаче.

Технический исполнитель не меняет методологию ради удобства вёрстки.

# 11. Курс / обучающая программа

Если выбран формат обучения, дизайн поддерживает освоение, а не презентационный блеск.

Нужны:

- ясный результат программы и модулей;  
- логическая последовательность;  
- практика;  
- проверка навыка/понимания там, где она нужна;  
- реальные или корректно маркированные учебные примеры;  
- связь материала с рабочим действием;  
- критерий освоения, а не только факт просмотра.

# 12. Клуб / библиотека / подписка

Если создаётся клуб или библиотека, UX должен помогать быстро найти ценность, а не превращаться в свалку материалов.

Нужны по мере роста:

- понятная навигация по проблемам/темам;  
- поиск/фильтры;  
- различение типов материалов;  
- актуальность/дата обновления;  
- связи между контентом и решениями;  
- понятный статус нового/обновлённого;  
- быстрый путь к применению.

# 13. Контентная точность

После фиксации content/logic производственный исполнитель не имеет права самовольно:

- менять методику;  
- сокращать критическое объяснение;  
- менять формулы/цифры;  
- добавлять факты;  
- ломать причинность;  
- присваивать известные методы Светлане;  
- менять юридически/финансово значимые формулировки без повторной проверки.

Если контент плохо помещается, проблема возвращается в продуктовый/UX-контур, а не маскируется микрошрифтом.

# 14. Читаемость и доступность

Конкретные размеры фиксируются production spec продукта.

Общие требования:

- ясная иерархия;  
- достаточный контраст;  
- читаемый основной текст;  
- разумная длина строки;  
- таблицы без перегруженного микротекста;  
- цвет не единственный носитель статуса;  
- интерактивные элементы визуально различимы;  
- достаточно воздуха без потери смысловой плотности;  
- мобильная/целевая читаемость фактически проверена.

Для цифровых продуктов по применимости дополнительно проверяются доступность и альтернативные способы восприятия/управления:

- смысловой нетекстовый контент получает понятную текстовую альтернативу/alt, если без неё теряется информация;  
- видео и аудио, где речь или звук несут содержание, получают субтитры, расшифровку или другой эквивалентный способ получить смысл;  
- интерактивные элементы доступны с клавиатуры там, где это технически применимо, имеют видимый focus и понятные названия/labels;  
- текст и интерфейс сохраняют смысл и управляемость при увеличении, reflow и на целевых узких экранах;  
- цвет, положение и анимация не являются единственным способом передать критический смысл;  
- для существенного motion по возможности предусмотрено уважение к настройке reduced motion или понятный немоушн-эквивалент, если отключение движения не разрушает функцию продукта.

Доступность не означает одинаковый интерфейс для всех. Требование — не закрывать человеку доступ к существенному содержанию или действию из-за способа представления, если проблему можно разумно устранить в выбранном формате.

# 15. Данные, цифры, графики и кейсы

Любая реальная цифра должна иметь источник/контекст либо явную маркировку демонстрационных данных.

График показывает реальный смысл и содержит показатель, единицы, период, источник/маркировку и понятный вывод.

Запрещены декоративная псевдоаналитика, ложное масштабирование и иллюзия точности без данных.

Реальный кейс называется реальным только при подтверждённой основе. Учебный пример маркируется как учебный/демонстрационный.

# 16. Роли в производстве

## Фабрика продуктов

Отвечает за результат пользователя, профессиональную основу, структуру, содержание, инструменты, пользовательский маршрут, критерии приёмки и production package.

## Бренд-система / Арт-директор

`02_Бренд-система` задаёт верхний визуальный код и ограничения бренда.

Арт-директор переводит их в визуальную концепцию конкретного продукта, прототип, производственную спецификацию и визуальный QA.

## Технический/производственный исполнитель

Выбирается по фактической задаче и получает утверждённый пакет. Не переизобретает продуктовую или бренд-стратегию.

# 17. Production package

До масштабной технической сборки должны существовать по применимости:

- актуальный MASTER/source of truth;  
- структура и пользовательский маршрут;  
- точные тексты;  
- формулы/логика;  
- источники, происхождение и права/лицензии внешних материалов по применимости;  
- примеры и маркировка данных;  
- утверждённый визуальный принцип;  
- прототипы сложных элементов;  
- состояния ошибок/пустых данных;  
- критерии тестирования;  
- список того, что нельзя менять без возврата в owner/product gate.

# 18. Один source of truth

Для каждого ключевого артефакта продукта существует один текущий мастер.

Итерационные исправления обновляют его; не плодить `финал2 / финал3` без реальной версии релиза.

Старые версии архивируются или явно маркируются как заменённые.

# 19. QA готового продукта

Минимальный общий QA:

- содержание не искажено;  
- обещанный пользовательский результат достижим в рамках продукта;  
- формулы/цифры проверены;  
- визуал помогает действию;  
- уровень прототипа сохранён по всему продукту;  
- нет деградации поздних страниц/экранов;  
- пользователь понимает входные данные, результат и следующий шаг;  
- целевые устройства/форматы проверены;  
- ссылки/кнопки/переходы работают;  
- нет обрезаний, наложений и служебных артефактов;  
- применимые legal/finance/data формулировки актуальны;  
- известные ограничения названы.

Самооценка `10/10` не заменяет acceptance gate.

# 20. Ремонт после QA

Сначала собирается полный список дефектов, затем выполняется консолидированное исправление по корневым причинам и регрессионная проверка.

Не возвращать Светлане по одной странице или одному дефекту, если система может собрать ремонт целиком.

Принятые стабильные части не трогаются без причины.

# 21. Критерий успешной дизайн-системы

Система работает, если новый продукт можно довести от утверждённой стратегии до профессионального пользовательского результата без:

- навязывания старого шаблона;  
- отраслевого retail-default там, где он неуместен;  
- постоянного участия Светланы в вёрстке;  
- потери содержания;  
- непонятных инструментов;  
- деградации качества к концу;  
- зависимости от одного сервиса;  
- визуального разрыва с брендом `Докрути`.
