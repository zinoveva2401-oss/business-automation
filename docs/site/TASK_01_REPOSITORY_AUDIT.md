# TASK_01_REPOSITORY_AUDIT

Статус: Готово к выполнению Qwen Coder  
Тип задачи: ТОЛЬКО АУДИТ  
Изменения файлов: ЗАПРЕЩЕНЫ  
Commit: ЗАПРЕЩЕН

## Цель

Провести технический аудит репозитория `business-automation` перед началом разработки нового сайта проекта «Розница в цифрах».

## Перед началом

1. Прочитай `QWEN.md`.
2. Прочитай `docs/site/SITE_SOURCE_OF_TRUTH_v1.1.md`.
3. Затем изучи текущую структуру репозитория.
4. Не меняй ни одного файла.

## Что нужно определить

### 1. Общая структура

Покажи дерево верхнего уровня репозитория и основные вложенные папки, имеющие отношение к:
- сайту;
- HTML;
- Astro;
- frontend;
- продуктам;
- GitHub Pages;
- GitHub Actions;
- документации.

Не нужно выводить тысячи файлов. Покажи только полезную структуру.

### 2. Есть ли уже сайт

Ответь:
- существует ли готовый/частично готовый сайт;
- где он расположен;
- на чём сделан;
- запускается ли он;
- есть ли `package.json`;
- есть ли Astro, Vite, React, Next.js или другой frontend stack.

### 3. Старые попытки разработки

Найди:
- старые HTML-лендинги;
- папки/файлы, похожие на незавершённый сайт;
- старые конфигурации GitHub Pages;
- старые workflow;
- старые инструкции агентам;
- старые бренд/контентные документы, которые могут конфликтовать с новым сайтом.

Ничего не удаляй.

### 4. Текущий GitHub Pages

Проверь только по файлам репозитория:
- есть ли workflow публикации;
- есть ли папка `docs` как потенциальный Pages source;
- есть ли `CNAME`;
- есть ли конфигурация сборки.

Если по репозиторию нельзя определить реальные настройки GitHub Pages, прямо напиши это.

### 5. Риски

Отдельно перечисли:
- что может конфликтовать с новым Astro-сайтом;
- что нельзя трогать без решения владельца;
- какие старые файлы могут вводить Qwen в заблуждение;
- есть ли риск сломать существующие продукты или автоматизации.

### 6. Рекомендованное место для нового сайта

Предложи ОДИН основной вариант, где разместить сайт внутри существующего репозитория: в корне, `/site`, `/website` или другое.

Но:
- не создавай папку;
- не перемещай файлы;
- только дай рекомендацию и объясни её.

### 7. Рекомендация по следующему этапу

После аудита предложи только один следующий технический этап. НЕ начинай его выполнять.

## Формат ответа

### А. Краткий вывод
5–10 строк.

### Б. Фактическая структура
Краткое дерево.

### В. Что уже существует
Таблица: `Объект | Путь | Статус | Что это`

### Г. Конфликты и устаревшие элементы
Таблица: `Файл/папка | Почему может конфликтовать | Что делать сейчас`

### Д. Рекомендация по расположению сайта
Один вариант + аргументация.

### Е. Что проверено фактически
Точный список проверок/команд.

### Ж. Что не удалось проверить
Без предположений.

### З. Статус

Напиши ровно:

`АУДИТ ЗАВЕРШЁН. ФАЙЛЫ НЕ ИЗМЕНЕНЫ. COMMIT НЕ СОЗДАН.`

## Критический запрет

НЕ:
- устанавливать зависимости;
- запускать миграции;
- создавать Astro;
- создавать ветку;
- делать commit;
- редактировать `README.md`;
- редактировать `AGENTS.md`;
- редактировать старую базу знаний;
- удалять или переносить файлы;
- «наводить порядок» по собственной инициативе.
