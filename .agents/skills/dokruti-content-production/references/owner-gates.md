# Owner gates

## Назначение
Обращайся к владельцу только за решением, которое нельзя безопасно вывести из утверждённых правил.

## Рабочая процедура
Продолжай низкорисковую обратимую работу, когда source/claim/rights/capability подтверждены. Gate обязателен для изменения frozen brand/strategy/product/legal решений; новой личной истории/identity; отсутствующего owner-only fact/asset; затрат; OAuth/credentials; высокорискового legal/financial вопроса; необратимой публикации/удаления без прямого разрешения. Различай draft approval и publish authorization.

## Выход и gate
Формат: конкретный выбор → почему важен → варианты и последствия → рекомендация → что изменится. Разрешение на недельный пакет может покрыть гибкий период (например, 7 дней, несколько дней, следующий день или один asset); не задавай фиксированный срок по умолчанию. Сохрани точные approved payload SHA-256, batch/authorization ID, каналы, valid_from/valid_until, expiry, допустимые изменения и evidence/decider. Публикация допускается только при совпадении хеша и канала и попадании планового времени в scope. Изменение контента вне явно разрешённых изменений требует нового решения. Все материалы пакета можно публиковать без ежедневного повторного подтверждения, пока они совпадают с разрешённым scope и действующим сроком.

Если approved buffer пуст или близок к истечению, продолжай производить и QA следующий сильный asset по live demand, затем запроси одно конкретное пакетное разрешение. Не останавливай независимую подготовку. Не эскалируй crop, микрокопирайт и safe technical choices. При gate удержи side effect, сохрани persistent checkpoint, продолжай независимые lanes.
