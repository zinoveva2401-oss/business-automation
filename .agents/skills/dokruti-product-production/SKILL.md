# DOKRUTI product production executor — autonomy, product-depth and knowledge-value overlay v1.3.0

For substantial product work, route first through the shared Core at `.agents/skills/ai-business-os/references/product-factory.md` and apply the versioned Product Factory domain overlay in `products/AGENTS.md`. The shared Core remains unchanged. Overlay v1.3.0 extends v1.2.0 for live owner decisions DEC-205/206: it classifies knowledge products, preserves the approved PROD-TEAM-001 education job, requires saturated discipline/direct-product research and actual package inspection where lawfully available, tests deep practical learning value and master/series choices, and keeps owner language simple.

This Skill supplies execution routing and must not turn an incomplete internal stage into an owner handoff:

1. Restore the exact product/task source and inspect existing target files before editing. Mark unavailable sources precisely; request owner access only when that access is a real prerequisite.
2. Translate a business-level instruction into the locked product identity and product type, complete applicable gate ledger, specialist route, sufficient evidence budget, market-saturation stop condition and acceptance criteria. Start research from the whole approved job; do not silently narrow the job to a proposed module or ask the owner to dispatch routine work.
3. If a criterion is missing or fails but is correctable, route it to the responsible specialist, repair it, recheck it and continue. Never stop merely to ask whether normal research or repair should proceed.
4. For coded or interactive output, follow `docs/PRODUCT_EXECUTION.md` and the approved product design/technical source. Keep changes inside the exact product folder and preserve unrelated products.
5. For knowledge products, plan depth and ready application support: clear explanations, why/when a method works or fails, real examples, worked scenarios, practical steps, useful ready tools and filled examples. Do not create unsupported homework, textbook language or an artificial page limit. Compare one deep product with a connected series or core-plus-advanced structure when scope may be too large.
6. Before any prototype, map the relevant discipline and SMB fit; saturate discovery of applicable methods and direct comparable self-serve digital products; inspect the buyer package through lawful previews/samples where available; prove paid value and the free-AI distinction; independently review Product Architecture; then write the complete eleven-part architecture report in simple Russian. If value or AI replaceability fails, redesign and recheck internally. The architecture report may go to the owner only as a complete, reviewed pre-prototype direction decision. Never bypass paid access or copy protected content.
7. Do not start a visual or representative prototype until the owner has explicitly approved the understandable architecture. Then build a meaningful end-to-end piece of the whole product, not an isolated micro-tool, in the evidence-supported format.
8. Inspect the actual artifact and close all applicable post-architecture research, commercial, legal/IP/claims, technical, visual/UX and independent review gates. Apply one consolidated correction pass, recheck corrected criteria and run regression review.
9. Before each owner handoff Architect/Supervisor asks `ARE ALL REQUIRED INTERNAL GATES CLOSED?` for that decision stage. If no, block the handoff and route open gates internally. An architecture approval does not waive post-prototype QA, and a prototype alone never closes internal gates.
10. Return only the decision package appropriate to the stage: first the reviewed architecture decision, then—if a genuine decision remains—the fully reviewed product/prototype package. Never ask the owner to inspect unfinished QA, choose specialists/tools, or authorize ordinary repair.
11. Do not publish, sell, change permissions, incur material spend or write to an external source unless that action is explicitly authorized in the parent task.

The Product Factory project is scoped to `products/`. Do not create Site, Content, Automation or Client Factory projects here. Future `CLIENT_WORK` must use the shared Core's conditional isolation boundary and the client's authorized project/state; never mix client and DOKRUTI data, brand, files, credentials or access.
