# DOKRUTI product production executor — autonomy and product-depth overlay v1.2.0

For substantial product work, route first through the shared Core at `.agents/skills/ai-business-os/references/product-factory.md` and apply the versioned Product Factory domain overlay in `products/AGENTS.md`. The shared Core remains unchanged. Overlay v1.2.0 extends autonomy v1.1.0 with product identity lock, full-job category research, paid-value and anti-trivialization gates, and a complete owner-readable Product Architecture Report before any prototype.

This Skill supplies execution routing and must not turn an incomplete internal stage into an owner handoff:

1. Restore the exact product/task source and inspect existing target files before editing. Mark unavailable sources precisely; request owner access only when that access is a real prerequisite.
2. Translate a business-level instruction into the locked product identity, complete applicable gate ledger, specialist route, sufficient evidence budget, stop condition and acceptance criteria. Start research from the whole approved job; do not silently narrow the job to a proposed module or ask the owner to dispatch routine work.
3. If a criterion is missing or fails but is correctable, route it to the responsible specialist, repair it, recheck it and continue. Never stop merely to ask whether normal research or repair should proceed.
4. For coded or interactive output, follow `docs/PRODUCT_EXECUTION.md` and the approved product design/technical source. Keep changes inside the exact product folder and preserve unrelated products.
5. Before any prototype, prove full-job market/category coverage, paid value and the free-AI distinction; independently review Product Architecture; then write the complete ten-part architecture report in simple Russian. If value or AI replaceability fails, redesign and recheck internally. The architecture report may go to the owner only as a complete, reviewed pre-prototype direction decision.
6. Do not start a visual or representative prototype until the owner has explicitly approved the understandable architecture. Then build a meaningful end-to-end piece of the whole product, not an isolated micro-tool, in the evidence-supported format.
7. Inspect the actual artifact and close all applicable post-architecture research, commercial, legal/IP/claims, technical, visual/UX and independent review gates. Apply one consolidated correction pass, recheck corrected criteria and run regression review.
8. Before each owner handoff Architect/Supervisor asks `ARE ALL REQUIRED INTERNAL GATES CLOSED?` for that decision stage. If no, block the handoff and route open gates internally. An architecture approval does not waive post-prototype QA, and a prototype alone never closes internal gates.
9. Return only the decision package appropriate to the stage: first the reviewed architecture decision, then—if a genuine decision remains—the fully reviewed product/prototype package. Never ask the owner to inspect unfinished QA, choose specialists/tools, or authorize ordinary repair.
10. Do not publish, sell, change permissions, incur material spend or write to an external source unless that action is explicitly authorized in the parent task.

The Product Factory project is scoped to `products/`. Do not create Site, Content, Automation or Client Factory projects here. Future `CLIENT_WORK` must use the shared Core's conditional isolation boundary and the client's authorized project/state; never mix client and DOKRUTI data, brand, files, credentials or access.
