# DOKRUTI product production executor — autonomy, product-depth and reader-experience overlay v1.4.0

For substantial product work, route first through the shared Core at `.agents/skills/ai-business-os/references/product-factory.md` and apply the versioned Product Factory domain overlay in `products/AGENTS.md`. The shared Core remains unchanged. Overlay v1.4.0 extends v1.3.1 with adaptive teaching, buyer-wide human language and reader-flow gates, instructional depth, distinct value/duplication review, authentic example provenance, cold-reader QA, whole-product transitions and tool comprehension.

This Skill supplies execution routing and must not turn an incomplete internal stage into an owner handoff:

1. Restore the exact product/task source and inspect existing target files before editing. Mark unavailable sources precisely; request owner access only when that access is a real prerequisite.
2. Translate a business-level instruction into the primary and supporting product types, approved product identity, complete applicable gate ledger, specialist route, sufficient evidence budget, market-saturation stop condition and acceptance criteria. Lock only an explicit approved buyer promise; otherwise set `PROMISED_RESULT = TO_DEFINE` and bring a clearly labelled proposal to the architecture decision. Start research from the whole approved job; do not silently narrow the job to a proposed module or ask the owner to dispatch routine work.
3. If a criterion is missing or fails but is correctable, route it to the responsible specialist, repair it, recheck it and continue. Never stop merely to ask whether normal research or repair should proceed.
4. For coded or interactive output, follow `docs/PRODUCT_EXECUTION.md` and the approved product design/technical source. Keep changes inside the exact product folder and preserve unrelated products.
5. For knowledge products, plan depth and ready application support: clear explanations, why/when a method works or fails, real examples, worked scenarios, practical steps, useful ready tools and filled examples. Do not create unsupported homework, textbook language or an artificial page limit. Compare one deep product with a connected series or core-plus-advanced structure when scope may be too large. For every workbook/tool component, answer all six value questions in `products/AGENTS.md`; reject it if practical value is unclear. A chapter does not automatically earn a spreadsheet tab.
6. Before any prototype, map the relevant discipline and SMB fit; saturate discovery of applicable methods and direct comparable self-serve digital products; inspect the buyer package through lawful previews/samples where available; prove the architecture's market/value logic and free-AI distinction; independently review Product Architecture; then write the complete eleven-part architecture report in simple Russian. Keep `REAL_BUYER_WTP` separate: it may be `UNKNOWN` for the architecture handoff, which must disclose that the architecture is a market-tested hypothesis and buyers' willingness to pay remains to be checked. Unknown WTP blocks full production/release, not visibility of an otherwise complete architecture. If architecture value logic is incomplete or free-AI replaceability is high, redesign and recheck internally. Never bypass paid access or copy protected content.
7. Do not start a visual or representative prototype until the owner has explicitly approved the understandable architecture. Then build a meaningful end-to-end piece of the whole product, not an isolated micro-tool, in the evidence-supported format.
8. Inspect the actual artifact and close all applicable post-architecture research, commercial, legal/IP/claims, technical, visual/UX and independent review gates. Apply one consolidated correction pass, recheck corrected criteria and run regression review.
9. Before each owner handoff Architect/Supervisor asks `ARE ALL REQUIRED INTERNAL GATES CLOSED?` for that decision stage. If no, block the handoff and route open gates internally. An architecture approval does not waive post-prototype QA, and a prototype alone never closes internal gates.
10. Return only the decision package appropriate to the stage: first the reviewed architecture decision, then—if a genuine decision remains—the fully reviewed product/prototype package. Never ask the owner to inspect unfinished QA, choose specialists/tools, or authorize ordinary repair.
11. For applicable knowledge/self-serve products, adapt the teaching/navigation structure to the buyer job and section; do not impose one universal chapter skeleton. Review the whole artifact for natural causal flow, varied rhythm, non-repeated value, sufficient explanation behind steps, supported example provenance and meaningful transitions.
12. Review every buyer-facing component—not just prose—for ordinary human language. Separately run independent cold-reader QA; producer clarity checks cannot certify reader experience.
13. For every working tool, require a cold reader to explain its purpose, use situation, inputs/data source, result, next decision, omissions, non-use boundary, complete example and first work session. Formula/function correctness alone does not pass.
14. Route correctable reader, instruction, duplication, example, transition or tool-comprehension defects to the specialist roles in the domain overlay; repair, recheck and regress before handoff.
15. Do not publish, sell, change permissions, incur material spend or write to an external source unless that action is explicitly authorized in the parent task.

The Product Factory project is scoped to `products/`. Do not create Site, Content, Automation or Client Factory projects here. Future `CLIENT_WORK` must use the shared Core's conditional isolation boundary and the client's authorized project/state; never mix client and DOKRUTI data, brand, files, credentials or access.
