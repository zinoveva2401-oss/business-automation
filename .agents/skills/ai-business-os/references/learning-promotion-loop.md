# Learning Promotion / Self-Improving Business OS v2.0.10

## Purpose

Let DOKRUTI improve from real work without turning every new trick into permanent instructions or allowing an external “self-learning” tool to rewrite the operating system unchecked.

## 1. Learning is evidence, not memory magic

A successful one-off result is a **candidate learning**, not automatically a Skill rule.

Capture:
`task / context / what failed or worked / evidence / why / reusable principle / limits / destination / regression needed / decision`.

## 2. Promotion destinations

Choose the smallest stable destination:
- `TASK/RUN NOTE` — one-off context only;
- `PROJECT PLAYBOOK` — reusable inside DOKRUTI but dynamic;
- `CHANNEL CARD` — platform-specific current learning;
- `PRODUCT/CONTENT METHOD` — stable domain method;
- `SKILL CORE/REFERENCE` — durable cross-task rule;
- `REJECTED LEARNING` — keep searchable so the failure is not repeated.

Do not put rapidly changing model names, trends, prices, UI details or algorithm folklore into the stable Skill core.

## 3. Promotion gate

Promote into a stable Skill/reference only when at least one applies:
- repeated across materially different tasks;
- a Critical/Major defect proves a missing durable rule;
- current owner operating model changed;
- independent evidence shows a stable cross-project method;
- security/legal/source architecture requires it.

Before promotion:
`source/freshness → conflict check → preservation map → targeted patch → regression → release/readback`.

## 4. Automatic proposal, controlled mutation

Business OS may automatically identify and draft a proposed learning. It may update dynamic playbooks/current task state when permissions and policy allow.

It must **not silently rewrite/install its canonical Skill package**. Stable Skill modification follows Skill Governance and owner-approved release/update path.

## 5. External self-learning tools

A plugin/repo/tool that claims to “teach the agent” is treated as a capability candidate, not authority.

Before adoption verify:
- what exactly it stores;
- where data lives;
- whether private project/customer data leaves our environment;
- how it selects learnings;
- whether it can mutate prompts/skills automatically;
- rollback/versioning;
- cost/licence/security;
- compatibility with ChatGPT/Codex surface;
- whether our existing playbook+regression mechanism already solves the need.

Preferred pattern:
`tool proposes learning → Business OS validates → regression → approved destination`.

Never allow unreviewed auto-backport into stable production rules.

## 6. Creative/content learning

For content/video/design experiments store the **mechanic and conditions**, not “copy this viral post”.

Example:
`split-layout talking head + contextual lower panel improved first-3-second retention for audience X under conditions Y` is a learning candidate.

`always use split-screen Reels` is not.

## 7. Closed loop

`EXECUTE → OBSERVE → DEFECT/SUCCESS → EXPLAIN → TEST AGAIN → ADOPT/ADAPT/REJECT → UPDATE PLAYBOOK/SKILL IF QUALIFIED → REGRESSION`.

## 8. Winner/loser and executor learning | r9 FINAL

Growth learnings store the failed/passed funnel stage, not a vague “post worked”. Executor learnings store the task class and actual artifact evidence, not a global opinion of a model/tool. Dynamic platform learnings update Platform Cards; executor graduation updates capability records; only durable cross-task principles enter stable Skill.
