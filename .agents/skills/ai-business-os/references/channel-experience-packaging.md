# Channel Experience / Packaging / Platform-Native Growth v2.0.10

## Purpose

Treat each public channel as a complete customer surface, not merely a place to repost content. The system must know how a person discovers the account, understands it, follows it, consumes a useful series, moves to another owned surface and eventually reaches a real offer — while current platform details remain dynamically verified.

## 1. One brand, different channel jobs

DOKRUTI keeps one positioning and evidence base across channels, but each channel may have a different primary job:
`DISCOVERY / SEARCH / TRUST / COMMUNITY / DEPTH / VIDEO / CONVERSION / RETENTION`.

Do not make channels artificially unrelated just to be “native”. Many people use only some platforms; the core promise and important ideas must remain recognizable wherever they meet the brand.

Native adaptation changes **presentation and interaction**, not truth.

## 2. Audience breadth without age stereotypes

Do not optimize only for young creators. For business content consider actual buyer/user/payer evidence, including middle-aged and older owners/founders/partners when they hold budget or decision power.

Age is not a proxy for ability or platform use. Use platform/account analytics, VOC and observed reach when available.

## 3. Channel Operating Card

Before material channel setup/growth work, create/update one current card instead of scattering rules across chats:

`platform / role / target audience state / profile promise / discovery surfaces / searchable fields / supported priority formats / cover-thumbnail-avatar rules / pinned or first-entry route / links-CTA / community behavior / bots-automation / analytics available / monetization route / ad-legal status / privacy-data risk / current official sources / last checked / experiments / what we learned`.

Update the existing card/row when the same channel already exists. Do not create a new channel task for every UI change.

## 4. Profile packaging

As applicable verify on the actual current interface:
- account/community name;
- searchable name/keywords without stuffing;
- handle/URL consistency;
- avatar recognizable at small size;
- bio/description: who this is for + why return;
- header/cover and mobile/desktop safe areas;
- pinned/featured entry content;
- contact methods;
- site/owned-channel links;
- current offer/CTA only when ready;
- trust proof;
- navigation/playlists/collections/series;
- thumbnail/cover family;
- recovery/ownership/2FA where relevant.

One identical cover image exported everywhere is usually not sufficient. Preserve brand system, adapt composition to each surface.

## 5. Covers / thumbnails / first frames

A cover or thumbnail is a decision surface, not decoration.

Check:
`one promise / visual hierarchy / small-size legibility / mobile crop / face-object relation / contrast / series recognizability / no false clickbait / match with delivered payoff`.

For platforms where autoplay makes the first frame more important than a separate cover, optimize the first visual event as the cover-equivalent.

## 6. Bots and automation

Do not install a bot merely because a platform supports one.

Bot/automation needs a specific job:
`navigation / FAQ / qualified inquiry / delivery / moderation / reminder / lead handoff / payment-support`.

Before setup verify current official platform/API rules, data/consent/legal constraints, cost, exportability, fallback and whether the same job can be handled more simply.

Stable repeated workflow first; automation second.

## 7. Platform algorithms and myths

Never store “the algorithm prefers X” as permanent Skill truth unless it is a durable documented platform constraint.

For material growth work:
1. check current official guidance where available;
2. inspect our account analytics/current interface;
3. use strong creator/agency observations only as hypotheses;
4. test with a bounded series;
5. write evidence back to the channel card/playbook.

One viral post is not a permanent algorithm rule.

## 8. Local/search/ad platforms

For platforms such as Yandex Business/Maps/Direct and equivalent local/search/ad systems, Business OS must route to a fresh platform-specialist execution mode:
- inspect current UI/account state;
- verify official current documentation, ad/legal/data requirements and billing;
- define business objective and conversion route;
- make exact setup changes only with permissions;
- capture before/after evidence;
- verify analytics/event path;
- document what was configured and rollback/ownership.

Do not sell or promise implementation work until DOKRUTI has proven the workflow itself or an external specialist route is verified.

## 9. Website ↔ video ↔ channel system

Video can strengthen explanation, trust, product understanding and session engagement, but never claim a direct search-ranking lift solely because “people stayed longer” unless current search-engine evidence supports that causal claim.

For site video decide its job:
`founder trust / explanation / demo / case / proof / onboarding / product preview / article enrichment`.

Then reuse/adapt the same production asset for appropriate channels where rights and format fit, without forcing every site video into every social surface.

## 10. Measurement and retention

Growth success is not “views”. Track the smallest useful set available for the job, e.g.:
`non-follower discovery / search impressions / first-seconds retention / average watch or read depth / completion / saves / shares / comments / follows / unfollows / profile visits / repeat viewers / channel-to-site clicks / qualified messages / orders / revenue`.

Unfollow/negative-feedback patterns matter. A channel that gains low-fit followers and loses trust is not successful.
