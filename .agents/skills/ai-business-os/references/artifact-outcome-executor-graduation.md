# Artifact Outcome Evals / Executor Graduation / Design-Before-Code | r9 FINAL

## Purpose

Stop confusing a strong instruction set with a strong result. A Skill, model, executor or tool earns responsibility only by producing final artifacts that pass representative DOKRUTI outcome tests.

## 1. Artifact outcome evals

For every high-value task class maintain representative real or fixture-based exams. Candidate classes include:
- Home / hero / key site page desktop + mobile;
- product page or product surface;
- final Telegram/VK/native post package;
- carousel/static visual;
- short video/reel/clip;
- long-form article;
- product/workbook/tool output;
- channel packaging;
- automation end-to-end publication/delivery;
- commercial purchase/first-value path when ready.

An outcome eval contains:
`TASK CLASS / exact input / current source snapshot / target reference or acceptance / actual final artifact identity / objective checks / independent specialist review / business-user outcome checks / defects / PASS-REWORK-BLOCKED / cost-time-owner rescue`.

String-presence tests and self-reports preserve architecture but **cannot certify premium output**.

## 2. Golden set and anti-overfit

Keep a small golden set of accepted DOKRUTI artifacts and negative baselines. Do not train the system to copy one layout or prose pattern. The test should check durable outcome qualities: specificity, evidence, hierarchy, usability, originality, mobile integrity, native fit, human language, payoff and business route.

Rotate representative tasks when the system can pass only one fixture but fails real work.

## 3. Executor scorecard by task class

Record evidence per executor/tool route:
`task class / current role / last verified / artifacts passed / repeated Major-Critical defects / owner rescue / latency / full cost / privacy-risk / best use / prohibited use / fallback`.

Do not label one executor globally “good” or “bad”. A route may be excellent for implementation and weak for art direction.

Allowed task-class role labels include `PRIMARY / SECONDARY / IMPLEMENTER-ONLY / REVIEWER-ONLY / FALLBACK / REJECTED`.

## 4. Graduation / demotion rule

An executor gains more autonomy only after representative PASS. Repeated materially similar Major/Critical defects trigger route repair or demotion.

Examples:
- repeated visual-template failure after rules are explicit → stop using the same executor as autonomous Art Director; keep it as implementer if implementation quality is proven;
- strong concept but repeated code regressions → separate concept and implementation roles;
- strong content structure but robotic language → route through founder voice/human-language specialist before publication;
- a plugin adds no measurable quality/time advantage → remove or keep as optional fallback.

Do not respond to repeated failure by endlessly adding prose to the same prompt unless evidence shows the missing instruction was actually the cause.

## 5. Design-before-code for premium surfaces

For material website/product visual work where art direction is a key acceptance dimension:

`CURRENT EVIDENCE → REFERENCE MECHANICS → 2–3 MATERIAL CONCEPTS WHEN NEEDED → SELECTED VISUAL SYSTEM → DESKTOP PROOF → MOBILE PROOF → MOTION/INTERACTION STORYBOARD WHEN MATERIAL → VISUAL FREEZE → IMPLEMENTATION → REAL BROWSER → INDEPENDENT VISUAL REVIEW`.

Code-first is allowed for low-risk utility/technical work where visual concept is not materially open. It is not the default for a premium redesign whose current blocker is visual originality/composition.

The freeze artifact can be Figma, a high-fidelity prototype, a rendered composition system, or another inspectable artifact. It must be specific enough that the implementation executor is not forced to invent the art direction while coding.

## 6. Reference fidelity without copying

Compare `BEFORE → SELECTED REFERENCE MECHANICS → FROZEN DOKRUTI CONCEPT → IMPLEMENTED AFTER`.

Extract mechanics, never protected expression 1:1. If the implemented page returns to generic card walls, dead-space headline grammar, stock decoration or mechanically repeated sections, FAIL even if build/tests pass.

## 7. External visual-production route

If available and justified, use a real visual-design surface for concept freeze before code. Tool choice is dynamic and can include Figma or another capable design system. Lack of a particular tool does not block the contract: choose another inspectable prototype route.

## 8. Acceptance

A task class is `EXECUTOR VERIFIED` only when the current exact route produced the final artifact, the independent review inspected that artifact, material acceptance passed, and no owner rescue was required beyond a true owner decision. `Skill exists`, `build passed`, `commit exists`, `agent said 10/10` are not graduation evidence.
