# Unified Content Owner Transaction v2.0.10 r8

## Purpose

DOKRUTI Content Factory is **one owner-facing production transaction**, not a chain of chats that Svetlana must coordinate.

The owner may give a short command such as:

`Подготовь на завтра пост для Telegram.`

The system must recover context, select the next eligible material, create the platform-native content and all required media, run internal professional QA, and show **one complete package for approval**. Svetlana must not rewrite the technical brief, choose internal specialists, open a separate Visual Factory, or manually transfer content between systems.

Radar may remain a separate scheduled research process, but it is an upstream evidence source, not a separate owner workflow. Content Factory reads Radar write-back and the existing Content System automatically.

## 1. One front door / hidden internal team

Internally the run may invoke:

`content strategist / editor / copywriter / creative director / art director / designer / image-video-media tools / SEO-search / platform-growth / analytics / legal-rights / critic`.

These are internal competencies. They do **not** become separate owner-facing chats, approval packets or handoffs.

Owner-visible rule:

`ONE REQUEST → ONE READY PACKAGE → ONE OWNER DECISION`.

A separate technical tool/process may exist behind the scenes only if it reduces owner work. Its output returns to the same content transaction before the package is shown to Svetlana.

## 2. Short-command autonomy / Existing queue first

When Svetlana says only `подготовь на завтра Telegram`, `сделай пост на завтра`, `подготовь контент на неделю` or an equivalent short instruction, do not ask her to restate the seven pains, topic taxonomy, format, visual style, CTA, time, source rows or technical acceptance.

Recover them from live sources.

Selection order:
1. current owner instruction;
2. active Content System calendar/queue;
3. existing eligible master topics before inventing a new one;
4. newest strong Radar signal only when it materially outranks the current queue;
5. current business/product/channel priorities;
6. own analytics/learning where available.

If 20+ existing topics are already planned, do not create a fresh topic merely because external research is interesting. Fresh research should enrich or reprioritize an existing material unless a genuinely new high-value signal is proven.

Ask Svetlana only if two materially different public commitments remain and professional routing cannot resolve them safely.

## 3. Queue selection gate

Before producing a public asset, inspect enough of the live queue to avoid repetition.

Choose the next eligible item by:
- publication window and current priority;
- current status and missing dependencies;
- duplicate output check;
- seven-pain balance;
- editorial-role balance;
- recent format/hook/visual repetition;
- freshness and evidence status;
- channel job and platform fit;
- current product/commercial readiness;
- existing analytics and prior learning;
- owner load and production cost.

Do not select a material only because it is first in a sheet if a newer decision, stale evidence or channel mismatch makes it a poor next publication.

## 4. Current Creative Intelligence Gate

For growth-important public content, do not rely on model memory or generic “social media best practices”. Before final creative direction, when freshness matters, perform a bounded current scan of applicable sources:

- Russia and the target local market;
- Europe and the US;
- China / wider Asia where relevant;
- official platform product/creator guidance;
- current winning creator/brand patterns;
- search/community/customer-language signals;
- DOKRUTI's own recent analytics and comments when available.

Build a small donor-mechanics set, usually 2–5 relevant candidates, in the internal form:

`SOURCE + DATE → OBSERVED MECHANIC → WHY IT MAY WORK → CONDITIONS → DOKRUTI ADAPTATION → RIGHTS/CLAIM RISK → TEST`.

**Never copy protected expression 1:1.** A foreign article, post, video, carousel, design or campaign may donate a topic signal, structure, mechanic, contrast, participation pattern, pacing idea or evidence trail. DOKRUTI must add its own Russian context, business reasoning, founder point of view, evidence and original execution.

Do not use a trend because it is fashionable. Use it only if it increases one intended behavior or improves understanding.

## 4.1. Editorial depth / product boundary

DOKRUTI public content must not default to complete mini-lessons. One content unit normally delivers **one strong idea + one micro-value**, for example: one small test, one criterion, one proven signal, one founder observation, one case/experiment, one contrarian correction or one participation question.

Portfolio rule: in any 5 consecutive publications, normally no more than 2 are direct how-to/diagnostic pieces unless current evidence justifies a temporary exception. Balance them with founder POV, current signal/reaction, case/proof, experiment, behind-the-scenes/build-in-public, question/participation, data story, myth/contrarian correction, tool/AI use or another channel-native editorial role.

A post/article may fully solve one narrow question. It should not casually give away the full multi-step methodology, templates, implementation cycle or integrated management system of an active paid product/service. The boundary is value architecture, not artificial withholding: the free piece must still be genuinely useful.

Primary portfolio outcome is not “teach something every day”. The content system must build attention, relevance, trust, authority, memorability, subscription intent, cross-channel movement and demand while preserving product value.

## 5. Behavior objective / growth job

Every output chooses **one primary intended behavior** before writing:

`STOP/OPEN → CONSUME → SAVE/SHARE → COMMENT/PARTICIPATE → PROFILE/SUBSCRIBE → SEARCH/CHANNEL/SITE → LEAD/PRODUCT`.

A single post does not need every step. Hook, format, visual and CTA should serve the chosen behavior and the channel's job.

Virality is a hypothesis, never a promise. The system should design for stronger stopping power, relevance, retention, sharing/subscription intent and downstream movement, then measure what actually happened.

## 6. Anti-boring / anti-template gate

A public asset fails pre-owner QA if it defaults to a generic lecture/checklist/card when a more native, vivid and current mechanism is available.

Before handoff ask:
- Would this look/sound interchangeable with 100 generic AI expert posts?
- Is the first screen/first visual event specific enough to stop the intended audience?
- Have the last 5–10 outputs repeated the same “pain → tips → CTA” grammar?
- Have portrait + big title, flat infographic, generic icons or identical card grids become a default?
- Can a real screen, object, work scene, number contrast, founder moment, mini-case, experiment, teardown, before/after, dialogue, carousel narrative, motion or participation mechanic communicate the idea better?

If yes, re-route before showing Svetlana.

## 7. Integrated asset production

Content Factory owns the **complete platform asset** required by the chosen format.

Examples:
- text-first Telegram post → final text; no decorative image required;
- image post → final text + actual image asset/preview;
- carousel → final copy + actual slide/card set, not merely a prompt describing it;
- short video → final script/storyboard/source plan and, when required inputs/tools are available, actual first cut/production asset; do not call a script a finished video;
- long-form/article → final article + required hero/inline visual assets when they materially improve the piece;
- screen/case post → actual verified screenshot/evidence with privacy/rights check.

A `VISUAL BRIEF` is an internal production instruction, **not a finished owner package** when the chosen route requires a visual.

If the necessary media capability or source asset is unavailable, return one exact blocker inside the same transaction. Do not send Svetlana to coordinate a separate Visual Factory.

If no visual is useful, explicitly mark `Визуал: не нужен — текстовый формат сильнее`.

## 8. Platform-native adaptation

One master idea may produce multiple channel assets, but only where each channel has a real job.

Do not copy the same text across Telegram, VK, Dzen, VC.ru, MAX, Instagram, site or video and call it adaptation.

For each selected platform determine:
- audience/context on that surface;
- intended behavior;
- native format/mechanic;
- hook and information order;
- media/crop/duration requirements;
- CTA / next step;
- measurement.

A platform may be skipped with a short internal reason.

## 9. Proposed publication time

Content Factory proposes the publication date/time together with the asset.

Priority:
1. DOKRUTI's own platform analytics for comparable audience/format/content role;
2. current platform-specific evidence;
3. bounded working hypothesis if data is insufficient.

Never present a generic “best posting time” as fact. When own data is insufficient, mark the slot as a test hypothesis and vary it deliberately so Analytics can learn.

## 10. Pre-owner internal council

Svetlana is an **approval owner, not a defect finder**.

Before a package reaches her, run only the applicable internal checks:
- content/editorial/human-language;
- audience/pain/benefit;
- hook/stop reason;
- current evidence/facts;
- creative/art/media quality;
- platform-native fit;
- product/commercial boundary;
- search/SEO/AEO only if relevant;
- legal/IP/privacy/advertising disclosure if relevant;
- analytics/experiment instrumentation;
- final render/file/readability/crop when media exists.

Fix obvious defects internally. Do not send a half-finished draft asking Svetlana to act as copy editor, art director or QA tester.

## 11. One owner package

Before public scheduling, show Svetlana one complete package per output:

`ID / PLATFORM / CONTENT ROLE / PRIMARY BEHAVIOR / HOOK / EXACT FINAL COPY OR SCRIPT / CTA / ACTUAL MEDIA PREVIEW OR “VISUAL NOT NEEDED” / PROPOSED DATE+TIME / WHY THIS IS NATIVE / ONE SHORT QA NOTE`.

For multi-platform production, present outputs sequentially or in a compact group that remains easy to review. If Svetlana asks to approve Telegram first, do not force review of all other platforms at once.

Owner answers in plain language. Exact commands are optional convenience, not required syntax:
- `утверждаю Telegram` or `УТВЕРЖДАЮ: TG-...`;
- `доработай начало` or `ДОРАБОТАТЬ: TG-... — ...`.

## 12. Public-content approval state machine

Until Svetlana explicitly changes this policy, DOKRUTI public content uses a mandatory owner gate **after internal QA and before scheduling**.

### Before approval
- Content System status: `На утверждении`.
- Publisher must ignore the row.
- Proposed date/time may be filled, but they are not permission to publish.

### Owner requests changes
- reuse the same output ID;
- repair the same asset;
- do not create a duplicate row;
- keep `На утверждении`;
- return the complete repaired package, not only the changed sentence/image fragment.

### Owner approves
Business OS must:
1. freeze the exact approved public payload: text/script, CTA, media asset/version, platform and approved date/time;
2. write the approved payload into the existing Content System row;
3. ensure required actual media URL/file is materialized when the format requires media;
4. set status `Запланировано` only after the row is publication-complete;
5. read back the row and verify exact text/media/date/time/status;
6. only then allow Publisher automation to pick it up.

No bot needs a separate owner instruction. Publisher is an executor that reacts to the canonical row state.

If the row changes materially after approval, return it to `На утверждении` unless the change is purely technical and cannot affect public meaning/render.

## 13. Publisher contract

Publisher must consume only publication-ready rows with the agreed status (currently `Запланировано`).

It does not decide:
- topic;
- wording;
- visual direction;
- CTA;
- publication strategy;
- owner approval.

It only executes the canonical payload, writes platform message/object ID, URL and actual time back, and reports errors.

## 14. Analytics learning

Publishing completes distribution, not learning.

Where technically available, Analytics Collector should attach actual post/channel metrics to stable content/output IDs, including only metrics that exist for the platform:

`reach/opens/views / retention or completion / saves / shares/forwards / comments/replies / reactions / follows/subscriber delta / profile visits / clicks / site actions / leads / sales / revenue`.

Content Factory reads these later by comparable:
`platform + editorial role + hook mechanic + format + pain + visual mechanic + CTA + time window`.

Missing metric = `UNKNOWN / DATA NOT AVAILABLE`, never a fabricated zero.

Analytics Collector can be a separate **technical service**, but not another owner-facing content agent. Its learning returns to Content System and the next Content Factory decision.

## 15. Acceptance / regression scenarios

The contract is working only if all of these hold:

A. Svetlana writes only `Подготовь на завтра пост для Telegram` and receives a complete review-ready package without technical prompting.

B. Existing queue material is reused before a new master topic is invented.

C. If the chosen format needs an image/carousel/video, the same content run produces or internally obtains the actual asset; a prompt/brief alone is not called ready.

D. Svetlana rejects the hook; the system repairs the same ID and returns the complete package.

E. Svetlana approves; the existing row becomes publication-complete and only then `Запланировано`; Publisher publishes without a second instruction.

F. A second platform uses a genuinely native adaptation, not a length-adjusted duplicate.

G. A current international trend is used as a mechanism donor with an original DOKRUTI adaptation, not copied expression.

H. Analytics later influences topic/format/hook/time selection without inventing missing metrics.

I. No separate owner-facing Visual Factory or approval chat is required.

J. One final owner package is understandable without internal workflow terminology.

## 16. r9 FINAL growth-program bridge

The short owner command still returns one finished content package, but the selection engine now reads the current Growth Program state when available. It may prioritize a winner continuation, loser repair, missing channel role, high-value audience question, return/retention asset or time-sensitive `SHIP-BY` signal over the next arbitrary queue row.

This does **not** authorize silent strategy changes or duplicate Content System objects. Reuse/update the same canonical topic/output/experiment IDs.

Founder-led packages also pass the current founder Voice Drift check when the task requires Svetlana's voice.
