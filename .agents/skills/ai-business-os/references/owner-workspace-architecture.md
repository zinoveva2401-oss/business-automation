# Owner Workspace Architecture / рабочее место и визуальный бизнес-кокпит Светланы

## Purpose

Business OS отвечает не только за бизнес-решения, но и за удобство работы Светланы. Он должен сам замечать, когда тексты, таблицы, папки и чаты уже создают лишнюю когнитивную нагрузку, и предлагать **лучший интерфейс поверх существующих источников**, не создавая вторую систему истины.

Главный вопрос:

> «Что Светлана сейчас вынуждена держать в голове, искать вручную или расшифровывать в тексте — и какой derived visual/interface слой снимет эту нагрузку?»

## 1. Workspace friction scan

Периодически и после крупных изменений проверяй:
- сколько источников надо открыть, чтобы понять «что происходит»;
- что приходится фильтровать/сводить вручную;
- где Светлана повторно спрашивает статус;
- где текстовая архитектура плохо воспринимается визуально;
- где план на неделю/месяц нельзя увидеть одним взглядом;
- где asset/content/product версии трудно сравнить;
- где метрики есть, но не ведут к решению;
- где одна таблица уже стала storage, а не удобным интерфейсом;
- где нет drill-down от красивой картинки к фактической строке/файлу;
- где нет нормального preview того, что будет опубликовано/продано.

## 2. Derived-view rule

Интерактивный дашборд, календарь, карта, канбан, таймлайн или визуальная архитектура **не становятся новой базой истины**.

Они должны:
`читать canonical sources → агрегировать/визуализировать → давать drill-down → сохранять минимум собственных display settings`.

Не заставляй Светлану поддерживать одинаковый статус вручную в Google Sheet и ещё одном dashboard.

## 3. Candidate owner interfaces

Предлагай только при реальной пользе.

### Executive Cockpit
Один экран:
`MAIN / этап / следующий результат / блокеры / деньги / готовность продукта / контент+каналы / продажи / сайт / автоматизация / решения Светланы / stale data`.

### Content Cockpit
`календарь неделя/месяц/квартал → master idea → канал-native версии → preview обложки/первого кадра → статус production → публикация → метрики → learning`.

Светлана должна видеть не только названия тем, но по возможности визуальный preview будущего материала.

### Commercial Architecture Map
Интерактивно:
`кому → какая боль/job → что продаём → proof → цена/экономика → канал → контент → CTA → оплата → выдача → повторная продажа`.

### Audience & Demand Map
Визуально:
`сегменты → боли → язык/VOC → контекст покупки → деньги/роль payer → каналы → контент-intent → продукты → evidence/unknowns`.

Не рисуй персонажей из фантазии: только evidence-backed карты.

### Product Portfolio
`NOW/NEXT/LATER/TEST/HOLD/KILL → readiness → спрос → доказательство → формат → цена/economics → зависимости → next gate`.

### Knowledge Capital Library
`решённая задача → метод → кейс/proof → reusable asset → контент → продуктовая возможность → где используется`.

### Portfolio / Case Gallery
`задача → before → решение → процесс → after/evidence → визуальный результат → что можно предложить клиенту`.

### Founder Learning Cockpit
`навык → диагностика → практика → применение в DOKRUTI → evidence → следующий уровень`.

## 4. When to recommend a dashboard

Dashboard оправдан, если выполняются несколько условий:
- данные приходят из нескольких источников;
- есть повторяющийся управленческий вопрос;
- нужен фильтр/период/drill-down;
- информация меняется регулярно;
- визуальная сводка экономит owner-hours;
- есть конкретное решение, которое принимается по экрану.

Если это одноразовая схема — лучше карта/документ/прототип, а не новый dashboard.

## 5. Visual-first preference

Для Светланы сложные системы по умолчанию объясняй **сначала визуальной логикой**, затем деталями:
`1 экран/карта → 3–7 главных блоков → связи → что делать → drill-down`.

Если текущая коммерческая архитектура/ЦА/контент-система понятна только после чтения длинного текста — это UX-дефект внутренней системы.

## 6. Proactive architecture gap scan

Business OS сам проверяет, не отсутствует ли decision-grade артефакт. Типовые кандидаты:
- buyer/audience evidence map;
- product portfolio;
- content operating calendar;
- executive dashboard;
- commercial visual master;
- offer/economics library;
- case/proof library;
- brand asset library;
- channel operating cards;
- experiment register;
- knowledge-capital register;
- capability/tool registry;
- founder learning map.

Но: **не создавать документ ради списка документов**. Для каждого кандидата сначала ответить:
`какое решение он улучшает / кто пользуется / как часто / из каких источников строится / почему текущего представления недостаточно`.

## 7. Client-reusable architecture

Внутренние системы DOKRUTI проектируй так, чтобы лучшие доказанные решения можно было потом безопасно превратить в:
- демонстрационный кейс;
- обезличенный demo-business;
- шаблон/методику;
- клиентский dashboard/operating system;
- implementation service.

Реальные приватные данные не используются как публичное demo без права/обезличивания.

## 8. Demo-business route

Если для портфолио нужен законченный пример, но собственный кейс ещё не готов или содержит приватные данные, можно построить **явно маркированный демонстрационный бизнес-кейс** на основе:
- реального прошлого опыта Светланы, если факты подтверждены и раскрытие допустимо;
- синтетического/обезличенного бизнеса с честной маркировкой `DEMO`, а не выдачей за клиента.

## 9. Acceptance

PASS, если предложенный интерфейс:
- решает конкретную owner-friction;
- не дублирует canonical data;
- визуально понятен;
- имеет drill-down;
- показывает freshness/unknowns;
- экономит время/ошибки;
- пригоден к будущей автоматизации;
- не требует от Светланы быть ручным синхронизатором.
