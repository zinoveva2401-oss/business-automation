# Work Production Controller / Research + Product Completion

## Purpose

Work is a production environment, not an independent business brain. DOKRUTI Business OS owns intent, source hierarchy, acceptance, owner gates and final verification. This module prevents Work from stopping on a report, audit, draft, prototype or nominal RC while the original business result is still incomplete.

## 1. Task compilation + immutable acceptance before execution

Before Work starts, Business OS must compile the task through [Task Specification & Delegation Compiler](task-specification-delegation.md). Work may not be asked to infer which prior version is approved, which known data/list is canonical, what may change, or what must remain frozen.

For substantial Work tasks create and preserve:

`MAIN / DELIVERABLE / ACCEPTANCE / SOURCE OF TRUTH / REQUIREMENT LEDGER / OWNER GATES / EVIDENCE / FINAL CUSTOMER PATH / STOP CONDITIONS / APPLICABLE QUALITY CONTRACTS`.

Business OS must inject the relevant detailed quality contracts before Work starts: editorial/human-language mode, universal output design/format-native presentation for all meaningful owner/customer/public artifacts, publication design for long-form, design thinking/visual system for substantial visual work, artifact architecture for products, media-production quality for video/motion/audio, plus domain-specific legal/commercial/technical gates.

The acceptance may be changed only by new owner decision or proven external blocker. Work may improve its route but may not silently shrink the promised result. A discovered implementation defect (for example a broken Excel formula) does not redefine a product task as only “fix Excel” while market/method/content/UX/delivery acceptance remains open.

## 2. Evidence-based execution state

A Work/Codex report is not the work product. Determine state from actual artifacts, runtime/readback and requirement evidence; never promote state only because the executor says `done`, `PASS` or lists changed files.

For every material deliverable maintain `REQ-ID → actual artifact location → evidence → PASS/FAIL/UNKNOWN`. If the artifact cannot be inspected, maximum state is `COMPLETED_UNVERIFIED`; if artifact inspection contradicts the report, state is `STOPPED_INCOMPLETE` with `COMPLETION INTEGRITY FAIL`.

After every Work report/tool log determine one state:

- `RUNNING` — real execution is still active;
- `WAITING_OWNER` — a genuine owner decision is required;
- `STOPPED_INCOMPLETE` — current run ended but acceptance is still open;
- `COMPLETED_UNVERIFIED` — all deliverables appear present but independent verification has not passed;
- `VERIFIED` — acceptance and final verification passed.

Never advise the owner to wait unless RUNNING is evidenced. If state is STOPPED_INCOMPLETE, Business OS must provide/execute the exact continuation route automatically.

## 3. Research completion contract

A research task is not complete because a report exists. It is complete only when:

- research intent is explicit: discovery / hypothesis test / monitoring / SKU selection;
- direct-peer definition is explicit;
- competitors are classified: `DIRECT PEER / ADJACENT / SUBSTITUTE / BENCHMARK / PARTNER`;
- discovery is performed before fitting results to our existing ideas;
- concrete SKU/product evidence is collected where product choice is involved;
- customer voice contains real public complaints/questions/reviews or clearly marked absence of evidence;
- product and service/manual-load economics are separated;
- rankings show `UNKNOWN` where evidence is missing;
- stated acceptance is actually answered; future research needed for acceptance is not disguised as a later recommendation.

## 4. Continuous competitor intelligence

Competitor work is cumulative and ongoing, not a frozen TOP list. Maintain a living competitor register when a canonical storage route exists. For each relevant founder-led peer track where publicly/legitimately accessible:

`person/brand / audience / positioning / products-SKUs / prices / contents / sales page / funnel / lead magnet / upsell / content formats / high-performing topics/videos where evidenced / reviews / complaints / strong mechanics / weak spots / changes / date / sources`.

New research should update the register, not rediscover the same people from zero.

## 5. New product command contract

When the owner says `сделай готовый продукт на тему X`, create/inherit the parent RUN and follow the current [Product Factory v2.0.10](product-factory.md), not a shortened legacy list. Minimum route:

1. Opportunity/problem evidence + disconfirmation.
2. Domain landscape before product structure.
3. Market/direct peers/product donors + full substitutes.
4. Founder claims/IP and productization gate.
5. Cheap experiment when a critical assumption is still uncertain.
6. Product thesis + format/learning fit + commercial/economic fit.
7. Frozen FULL PRODUCT MATRIX.
8. PRODUCT CONTENT BLUEPRINT for complex digital/long-form products.
9. Whole-artifact production with continuity and cross-component traceability.
10. Multi-discipline QA + one consolidated repair loop.
11. Independent verification of the actual client/SEND ONLY package.
12. Commercial packaging/delivery + Growth/Distribution package.
13. E2E purchase/first-value test before public sale.
14. Launch/money write-back + learning/portfolio decision.

If another route is materially better than a standalone product, return `OTHER FORMAT / EXPERIMENT / STOP` rather than forcing production. Do not ask the owner to choose an internal method/framework when experts can choose. If a genuine material decision remains, use the Owner Question Contract.

## 6. Donor / adaptation protocol

Required logic:

`SOURCE → PRODUCT/MECHANIC → WHY IT SELLS/WORKS → CUSTOMER PRAISE/COMPLAINT → ABSTRACT PRINCIPLE → DOKRUTI IMPROVEMENT → ORIGINAL IMPLEMENTATION → IP/LEGAL CHECK`.

It is allowed and encouraged to benchmark product structure, functional mechanics, onboarding, funnel steps, packaging logic, price ladders, content formats and user-flow patterns. It is not allowed to copy protected expression 1:1: copyrighted text, proprietary code, branded visual composition, private/licensed files, trademarks presented as ours, or closed materials obtained without authorization.

## 7. Product release manifest

Before Work may claim a product is complete, produce a factual release manifest:

`customer deliverable / exact file or URL / version / purpose / opens? / functional QA / visual QA / legal state / customer step / PASS-FAIL`.

The manifest must match actual files. A promised file that is absent or an RC version mismatch is a Major defect.

## 8. Full-path product QA

Test the product as a buyer, not as an author:

`discover/buy → receive → open START HERE → open main product → use core tool/template → understand next action → access every promised file → complete first result → know support/update/license boundaries`.

Where formats require it, actually open/render/execute them. Merely seeing a filename or formula is not sufficient evidence.

Release requires `Critical = 0` and `Major = 0`.

## 9. Independent verification

The producing Work pass cannot self-certify VERIFIED. Use a real independent subagent/verifier when available; otherwise run a separately scoped verification pass that receives the original task + immutable acceptance and is instructed to find FAIL/UNKNOWN, not to defend the producer.

Any FAIL/UNKNOWN returns to repair and regression.

## 10. Owner Question Contract

A question to Светлана must use this form:

`ЧТО ВЫБИРАЕМ` — plain Russian description.
`ПОЧЕМУ ЭТО ВАЖНО` — business consequence.
`ВАРИАНТ 1` — what it means, pluses, minuses.
`ВАРИАНТ 2` — same.
`МОЯ РЕКОМЕНДАЦИЯ` — one recommended option and why.
`ЧТО ИЗМЕНИТСЯ ПОСЛЕ РЕШЕНИЯ` — downstream effect.

No unexplained English terms, framework labels or internal architecture jargon.

## 11. Owner-facing handoff

The final owner-facing message starts with:

`ЧТО ГОТОВО / ЧТО ПРОВЕРЕНО / ЧТО НУЖНО ОТ СВЕТЛАНЫ`.

Do not dump internal research logs, defect registers or agent debates unless they are needed for an owner decision or requested explicitly.


## 12. Stage packet rule

For a multi-stage product, the parent acceptance remains whole, while each internal stage gets its own execution packet. If revalidation can change the product architecture, do not package final files in the same packet. If a visual/product choice is frozen, later repair packets must name that frozen baseline and may not reopen it without evidence + owner gate.

## 13. Customer-experience production rule

Work may not increase perceived completeness by multiplying formats/files. Before product packaging, run artifact rationalization against [product-experience-artifact-architecture.md](product-experience-artifact-architecture.md). For long-form run [editorial-reader-experience.md](editorial-reader-experience.md) before [publication-design-ebook.md](publication-design-ebook.md). For substantial visual work run [design-thinking-visual-system.md](design-thinking-visual-system.md) with an independent critic.

A Work run that fixes formulas but leaves text/narrative/product architecture/UX acceptance open remains STOPPED_INCOMPLETE, not VERIFIED.
